MONOTONIC READS (MR) – NORMAL OPERATION
FINAL EXPERIMENT DESIGN


1. OBJECTIVE
------------

The purpose of this experiment is to investigate whether Apache Cassandra
provides monotonic-read consistency under different combinations of read
and write consistency levels.

Monotonic-read consistency means:

Once a client has observed a particular version of a value, a later read
by the same client should never return an older version.

Example:

    Read sequence:

    v1 -> v1 -> v2 -> v2 -> v2

    Result: PASS

The client moves from an older version to a newer version and never moves
backwards.


Example:

    v1 -> v2 -> v1 -> v2 -> v2
               ^
               |
          MR VIOLATION

The client observed v2 and subsequently observed the older v1.


IMPORTANT:

A stale read is NOT automatically a monotonic-read violation.

For example:

    v1 -> v1 -> v1 -> v1 -> v1

may be stale if v2 has already been written, but it still satisfies
monotonic reads because the client's observations never move backwards.



2. DATABASE CONFIGURATION
-------------------------

The experiment uses three Apache Cassandra Docker containers:

    cassandra1
    cassandra2
    cassandra3

All nodes belong to:

    datacenter1

Replication factor:

    RF = 3

Therefore, each experimental partition is replicated across all three
Cassandra nodes.

The consistency levels investigated are:

    ONE
    QUORUM
    ALL


Both the WRITE consistency level and READ consistency level are varied.

Therefore, nine configurations are tested:

    WRITE ONE     / READ ONE
    WRITE ONE     / READ QUORUM
    WRITE ONE     / READ ALL

    WRITE QUORUM  / READ ONE
    WRITE QUORUM  / READ QUORUM
    WRITE QUORUM  / READ ALL

    WRITE ALL     / READ ONE
    WRITE ALL     / READ QUORUM
    WRITE ALL     / READ ALL



3. NETWORK CONDITION
--------------------

All Cassandra nodes run as Docker containers on the same physical
computer.

Without network emulation, communication between the containers is
extremely fast compared with many real distributed deployments.

The following Linux netem configuration is therefore applied:

    tc qdisc replace dev eth0 root netem delay 25ms 25ms

This introduces:

    25 ms nominal/base delay
    25 ms jitter

The purpose is to introduce variable network timing and avoid the
near-zero communication delay of co-located Docker containers.

All three Cassandra nodes remain connected and operational during the
normal-operation experiment.

The same baseline network configuration is retained across the
client-centric consistency experiments.



4. COORDINATOR SELECTION
------------------------

The Cassandra nodes are exposed separately:

    cassandra1 -> localhost:9042
    cassandra2 -> localhost:9043
    cassandra3 -> localhost:9044

The experiment maintains a client session associated with each exposed
node.

For the experimental write, one node is selected at random to act as the
coordinator.

For each subsequent read, a coordinator is independently selected again.

Therefore, the five reads in one trial may use different coordinators.

Example:

    WRITE v2 -> cassandra1

    READ 1 -> cassandra3
    READ 2 -> cassandra1
    READ 3 -> cassandra2
    READ 4 -> cassandra3
    READ 5 -> cassandra1

This creates opportunities for the same logical client to observe
different parts of the distributed system.



5. NUMBER OF TRIALS
-------------------

Each of the nine WRITE/READ consistency configurations is tested using:

    200 requested trials

Therefore:

    9 x 200
    = 1,800 requested trials

Each measured trial contains:

    1 experimental write
    5 consecutive reads

Therefore, a fully completed experiment can contain up to:

    1,800 x 5
    = 9,000 read observations.



6. EXPERIMENTAL PREPARATION
---------------------------

Every trial uses a unique key.

Before the measured experiment begins, version 1 is established using:

    WRITE CL = ALL

Conceptually:

    Node 1 = v1
    Node 2 = v1
    Node 3 = v1

Using ALL provides a known initial state acknowledged by all three
replicas.


Because this operation is only experimental preparation, it may be
retried up to three times if a timeout occurs.

A failure during preparation is recorded as:

    SETUP_ERROR

and is NOT considered a monotonic-read violation.

This distinction prevents failure to establish the experimental starting
condition from being confused with the behavior being measured.



7. MEASURED EXPERIMENT
----------------------

Once v1 has been successfully established, the measured trial begins.


STEP 1 – WRITE

The logical client writes:

    version = 2

using the WRITE consistency level being tested.

A coordinator is selected independently at random.

The program waits until Cassandra reports that the write has completed
successfully.

There is no retry for the experimental write.

If the write cannot complete, the trial is recorded as:

    ERROR


STEP 2 – FIVE IMMEDIATE READS

Immediately after the successful write, the same logical client performs:

    READ 1
    READ 2
    READ 3
    READ 4
    READ 5

using the READ consistency level being tested.

There is no artificial sleep between these reads.

A coordinator is independently selected for every read.

The resulting client history might therefore look like:

    [1, 1, 2, 2, 2]

or:

    [2, 2, 1, 2, 2]



8. DETECTING A MONOTONIC-READ VIOLATION
---------------------------------------

Every observed version is compared with the previous version observed by
the same logical client.

If:

    current version >= previous version

there is no regression.


Examples:

    1 -> 1     valid
    1 -> 2     valid
    2 -> 2     valid


If:

    current version < previous version

a monotonic-read violation has occurred.


Example:

    previous observation = v2
    current observation  = v1

Therefore:

    v2 -> v1

is an MR violation.



9. EXAMPLE TRIALS
-----------------

Example A:

    [1, 1, 1, 2, 2]

Result:

    PASS

Although the early reads are stale relative to the successful v2 write,
the client's observations never move backwards.


Example B:

    [2, 2, 2, 2, 2]

Result:

    PASS


Example C:

    [1, 2, 1, 2, 2]

Result:

    FAIL

The transition:

    2 -> 1

is a monotonic-read violation.


Example D:

    [2, 1, 1, 2, 2]

Result:

    FAIL

The first transition already moves backwards.



10. TRIAL CLASSIFICATION
------------------------

PASS:

    All five reads complete and no backwards transition occurs.


FAIL:

    All required operations complete, but at least one backwards
    transition is observed.


ERROR:

    The measured experimental write or one of the five reads cannot
    complete.


SETUP_ERROR:

    The initial v1 state could not be established after the permitted
    setup retries.

SETUP_ERROR is kept separate because the actual experiment never began.



11. PREDICTIONS BEFORE RUNNING THE EXPERIMENT
---------------------------------------------

Before examining the final results, the following qualitative predictions
were made.


WRITE ONE / READ ONE

    Monotonic-read violations are possible.

    After WRITE ONE succeeds, some replicas may still contain v1 while
    another contains v2.

    Repeated READ ONE operations can therefore potentially observe:

        v1 -> v2 -> v1

    which violates monotonic reads.


WRITE ONE / READ QUORUM

    Violations may be possible, but are expected to be less likely than
    ONE/ONE.

    No particular non-100% success rate is assumed in advance.


WRITE ONE / READ ALL

    No violations expected.


WRITE QUORUM / READ ONE

    Violations are possible.

    A successful QUORUM write requires two replica acknowledgements, but
    a remaining replica may temporarily contain the older value.

    READ ONE may therefore potentially observe a newer replica followed
    by the stale replica.


WRITE QUORUM / READ QUORUM

    No violations expected.


WRITE QUORUM / READ ALL

    No violations expected.


WRITE ALL / READ ONE

    No violations expected.


WRITE ALL / READ QUORUM

    No violations expected.


WRITE ALL / READ ALL

    No violations expected.


These predictions describe possible/expected behavior and are kept
separate from the empirical observations.

13. MAIN OBSERVATIONS
---------------------

Actual monotonic-read regressions were observed for:

    WRITE ONE / READ ONE

and:

    WRITE QUORUM / READ ONE


For ONE/ONE:

    3 of 200 trials contained a regression.

For QUORUM/ONE:

    3 successfully measured histories contained a regression.


No regressions were observed for:

    ONE / QUORUM
    ONE / ALL

    QUORUM / QUORUM
    QUORUM / ALL

    ALL / ONE
    ALL / QUORUM
    ALL / ALL


Importantly, the absence of observed violations does not by itself prove
that every such configuration universally guarantees monotonic reads.



14. WHY RYW AND MR RESULTS DIFFER
---------------------------------

The RYW experiment produced substantially more violations in weak
configurations than the MR experiment.

This is not contradictory because the two properties test different
conditions.


RYW asks:

    "I successfully wrote v2. Does my next read observe v2?"

Therefore:

    write v2
    read v1

is immediately an RYW violation.


MR asks:

    "Given what I have already observed, do my subsequent observations
    ever move backwards?"

Therefore:

    v1 -> v1 -> v1 -> v2 -> v2

satisfies monotonic reads even though several reads returned the old
version after v2 had already been written.


A stale read therefore violates RYW much more easily than it violates MR.

For MR, the client must first observe the newer value and subsequently
observe an older value.



15. AVAILABILITY AND CONSISTENCY ARE RECORDED SEPARATELY
--------------------------------------------------------

Timeouts are not classified as monotonic-read violations.

For example, a Cassandra ReadTimeout means that Cassandra did not obtain
enough replica responses before the timeout.

It does NOT mean Cassandra returned an older version.

Therefore, the experiment separately reports:

    consistency success
    consistency violations
    experimental errors
    setup errors
    availability


This distinction becomes particularly important in the later node-failure
and network-partition scenarios.

17. PRIMARY METRIC
------------------

The primary consistency metric is:

                         MR passes
    MR success rate = -------------------
                      completed MR trials


Only completed histories are used to calculate the consistency success
rate.

Availability is reported separately.



18. SECONDARY METRIC
--------------------

The experiment also reports:

                               regression events
    read regression rate = ---------------------------
                           completed read observations


This gives two perspectives:

    MR success rate
        -> How often did an entire client history satisfy MR?

    Regression rate
        -> How frequently did an individual backwards transition occur?



19. LIMITATION
--------------

The measured success rates are empirical results for this particular
deployment and experimental workload.

For example:

    ONE / ONE MR success = 0.985

does NOT mean Cassandra inherently provides monotonic reads with a 98.5%
probability.

The observed rate depends on factors including:

    network timing
    coordinator selection
    Docker scheduling
    Cassandra replica propagation
    workload
    number of reads per trial
    number of trials

Similarly:

    200/200 successful trials

means that no violation was observed in those trials. Experimental
observation should not automatically be interpreted as a universal
theoretical guarantee.


================================================================================
MONOTONIC READS (MR) CONSISTENCY – NODE FAILURE EXPERIMENT DESIGN
================================================================================

1. OBJECTIVE
------------
The purpose of this experiment is to evaluate whether Apache Cassandra preserves
Monotonic-Read (MR) consistency when a single replica crashes after a write
has completed.

Monotonic Reads requires that if a logical client observes version v_a at logical
time t1, any subsequent read by the same logical client on that key at logical
time t2 > t1 must never observe an older version v_b < v_a.

Under single-node crash-stop failure (RF=3):
- Replicas: cassandra1, cassandra2, cassandra3.
- Target failed node: cassandra3 is stopped during the degraded read phase.
- Surviving nodes: cassandra1, cassandra2 remain online and handle the two sequential reads.


2. CORE MONOTONICITY CHECK
--------------------------
A single client performs two sequential reads (Read 1 and Read 2):
- Read 2 is executed ONLY after Read 1 has successfully completed.
- Core check:
      first_read_version <= second_read_version

Outcomes:
- v1 -> v1 : PASS (stale read, but non-decreasing: version did not regress)
- v1 -> v2 : PASS (monotonic version progression)
- v2 -> v2 : PASS (fresh read consistently maintained)
- v2 -> v1 : MR_VIOLATION (regression where reader observed newer then older version)


3. CONFIGURATION MATRIX
-----------------------
All 9 combinations of Write CL x Read CL are evaluated:
  - WRITE ONE     / READ ONE
  - WRITE ONE     / READ QUORUM
  - WRITE ONE     / READ ALL
  - WRITE QUORUM  / READ ONE
  - WRITE QUORUM  / READ QUORUM
  - WRITE QUORUM  / READ ALL
  - WRITE ALL     / READ ONE
  - WRITE ALL     / READ QUORUM
  - WRITE ALL     / READ ALL


4. PER-TRIAL EXECUTION LIFECYCLE
--------------------------------
Phase 1: Pre-trial Health Verification
  - Query nodetool status: verify all 3 nodes report 'UN'.
  - Query nodetool describecluster: verify Live=3, Unreachable=0, schema agreed.
  - Verify native CQL ports (9042, 9043, 9044) are open.

Phase 2: Baseline State Establishment (v1)
  - Write initial version v1 with CL=ALL while all 3 nodes are healthy.
  - Setup coordinator is selected strictly from surviving majority nodes
    (cassandra1, cassandra2) and re-randomized inside the retry loop.
    This prevents coupling pre-trial setup to transient socket recovery of cassandra3.

Phase 3: Writer Write (v2)
  - Writer writes v2 at tested write_cl across the healthy 3-node cluster.
  - Write coordinator is selected from all 3 healthy nodes (cassandra1, cassandra2, cassandra3).

Phase 4: Node Failure Injection
  - Gracefully close client session to cassandra3.
  - Stop container cassandra3 ('docker stop -t 2 cassandra3').
  - Verify container is stopped ('docker inspect').

Phase 5: Two Degraded Sequential Reads (Read 1 & Read 2)
  - The client issues Read 1 at read_cl via an independently chosen surviving coordinator
    (cassandra1 or cassandra2).
  - Only after Read 1 completes, the client issues Read 2 at read_cl via an independently
    chosen surviving coordinator.
  - If read_cl == ALL: Cassandra cannot satisfy ALL (requires 3, only 2 alive).
    This raises an exception (e.g. UnavailableException or ReadTimeout) and is
    classified as OPERATION_FAILURE (UNAVAILABLE_ALL / READ_TIMEOUT), NOT an MR violation.

Phase 6: Node Recovery and Cluster Healing (finally block)
  - Restart container cassandra3 ('docker start cassandra3').
  - Poll until all 3 nodes report 'UN', ports open, Live=3, Unreachable=0,
    and schema agreement is restored.

Phase 7: Post-Recovery Reconciliation Probe
  - Issue read at CL=QUORUM across healed cluster to record reconciled state.

Phase 8: Trial Logging
  - Record complete trial parameters, coordinators, read 1/2 versions,
    regression flag, classification, and failure mechanism into node_failure.csv.


5. CLASSIFICATION TAXONOMY
--------------------------
1. PASS:
   first_read_version <= second_read_version (non-decreasing sequence).

2. MR_VIOLATION:
   first_read_version == 2 and second_read_version == 1 (regression).

3. OPERATION_FAILURE:
   Operation could not complete due to availability constraints:
   - UNAVAILABLE_ALL / READ_TIMEOUT on CL=ALL reads while 1 node is stopped.
   - WRITE_TIMEOUT on write operations.
   Failed operations are NEVER classified as MR violations.

4. SETUP_ERROR:
   Pre-trial baseline write (CL=ALL) failed after retries prior to injection.


6. OUTPUT ARTIFACTS
-------------------
- monotonic_reads/results/node_failure.csv (raw trial observations)
- monotonic_reads/results/node_failure_summary.csv (aggregated metrics)


================================================================================
MONOTONIC READS (MR) CONSISTENCY – NETWORK PARTITION EXPERIMENT DESIGN
================================================================================

1. OBJECTIVE
------------
The purpose of this experiment is to evaluate whether Apache Cassandra preserves
Monotonic-Read (MR) consistency when a symmetric network partition isolates a
minority node from the majority cluster while client reads traverse partition
boundaries.

Monotonic Reads requires that if a logical client observes version v_a at logical
time t1, any subsequent read by the same logical client on that key at logical
time t2 > t1 must never observe an older version v_b < v_a.


2. TOPOLOGY AND PARTITION MECHANICS
-----------------------------------
The 3-node cluster (RF=3) is divided into:
- Majority Component (M): cassandra1 (172.18.0.3), cassandra2 (172.18.0.4)
- Minority Component (I): cassandra3 (172.18.0.2)

Partition injection utilizes Linux kernel blackhole routing tables on all three
containers:
- cassandra1: ip route replace blackhole 172.18.0.2
- cassandra2: ip route replace blackhole 172.18.0.2
- cassandra3: ip route replace blackhole 172.18.0.3
- cassandra3: ip route replace blackhole 172.18.0.4

This drops internode packets between {c1, c2} and {c3} with zero TCP RST or ICMP
unreachable signals.
The link between cassandra1 and cassandra2 remains intact with normal latency.


3. ANOMALY MECHANISM: MONOTONIC READ REGRESSION (v2 -> v1)
----------------------------------------------------------
Under a network partition:
1. When v2 is written to the majority component (M) at CL=QUORUM or CL=ONE:
   - Replicas in M (c1, c2) receive the v2 update.
   - The minority node (c3) receives no messages and retains baseline v1.
2. If a single client issues Read 1 to Majority (M) at CL=QUORUM or CL=ONE:
   - Read 1 returns v2.
3. If that same client subsequently issues Read 2 to Minority (I, cassandra3) at CL=ONE:
   - cassandra3 serves the read locally from its storage engine without consulting M.
   - cassandra3 returns baseline v1.
4. Result: The client observes v2, and then observes v1 (v2 -> v1).
   This is an empirical Monotonic-Read violation (MR_VIOLATION).

Similarly:
- Writing v2 to Minority (I) at CL=ONE updates cassandra3 locally.
- Read 1 to Minority (I) returns v2.
- Read 2 to Majority (M) at CL=ONE contacts c1/c2, which never received v2 and
  return baseline v1.
- Result: v2 -> v1 MR_VIOLATION.


4. THE 9 EXPLICIT COORDINATOR ROUTING PATHS (P1–P9)
---------------------------------------------------
Path P1: Intra-majority quorum
  - Routing: Write M -> Read 1 M -> Read 2 M
  - Levels: W=QUORUM, R1=QUORUM, R2=QUORUM
  - Expected: PASS (v2 -> v2; quorum intersection across M guarantees monotonicity)

Path P2: Cross-component regression
  - Routing: Write M -> Read 1 M -> Read 2 I
  - Levels: W=QUORUM, R1=QUORUM, R2=ONE
  - Expected: MR_VIOLATION (v2 -> v1; R1 reads updated M, R2 reads isolated I)

Path P3: Cross-component regression
  - Routing: Write M -> Read 1 M -> Read 2 I
  - Levels: W=ONE, R1=ONE, R2=ONE
  - Expected: MR_VIOLATION (v2 -> v1; R1 reads updated M, R2 reads isolated I)

Path P4: Intra-minority local MR
  - Routing: Write I -> Read 1 I -> Read 2 I
  - Levels: W=ONE, R1=ONE, R2=ONE
  - Expected: PASS (v2 -> v2; all operations confined to isolated minority node)

Path P5: Cross-component regression
  - Routing: Write I -> Read 1 I -> Read 2 M
  - Levels: W=ONE, R1=ONE, R2=ONE
  - Expected: MR_VIOLATION (v2 -> v1; R1 reads updated I, R2 reads untouched M)

Path P6: Intra-majority local MR
  - Routing: Write M -> Read 1 M -> Read 2 M
  - Levels: W=ONE, R1=ONE, R2=ONE
  - Expected: PASS (v2 -> v2; both reads hit majority component)

Path P7: Intra-majority quorum write / local reads
  - Routing: Write M -> Read 1 M -> Read 2 M
  - Levels: W=QUORUM, R1=ONE, R2=ONE
  - Expected: PASS (v2 -> v2; quorum write acknowledged across {c1, c2})

Path P8: Write availability boundary
  - Routing: Write M -> Read 1 M -> Read 2 M
  - Levels: W=ALL, R1=ONE, R2=ONE
  - Expected: OPERATION_FAILURE (WRITE_TIMEOUT; ALL requires 3 nodes, only 2 reachable)

Path P9: Read availability boundary
  - Routing: Write M -> Read 1 M -> Read 2 M
  - Levels: W=ONE, R1=ONE, R2=ALL
  - Expected: OPERATION_FAILURE (READ_TIMEOUT; ALL read requires 3 nodes, only 2 reachable)


5. PER-TRIAL EXECUTION LIFECYCLE
--------------------------------
Phase 1: Pre-trial Health Verification
  - Query nodetool status: verify all 3 nodes report 'UN'.
  - Query nodetool describecluster: verify Live=3, Unreachable=0, schema agreed.
  - Verify native CQL ports (9042, 9043, 9044) are open.

Phase 2: Baseline State Establishment (v1)
  - Write initial version v1 with CL=ALL while all 3 nodes are healthy.
  - Setup coordinator is selected strictly from majority nodes (cassandra1, cassandra2)
    and re-randomized inside the retry loop.
    This guarantees baseline setup never hangs on transient socket reconnection
    to cassandra3 following previous healing cycles.

Phase 3: Inject Symmetric Network Partition
  - Install blackhole routes on cassandra1, cassandra2, and cassandra3.
  - Sleep 1.0s to allow kernel route tables to take effect.

Phase 4: Writer Write (v2)
  - Issue write at path's write_cl via assigned write coordinator component.
  - If write fails (e.g. CL=ALL in P8), classify as OPERATION_FAILURE and skip reads.

Phase 5: Two Degraded Sequential Reads (Read 1 & Read 2)
  - Issue Read 1 at read1_cl via assigned read1 coordinator component.
  - Only after Read 1 completes, issue Read 2 at read2_cl via assigned read2 coordinator component.
  - If Read 1 fails (e.g. timeout), classify as OPERATION_FAILURE and skip Read 2.
  - If Read 2 fails (e.g. CL=ALL in P9), classify as OPERATION_FAILURE.
  - If both complete:
    - If read1_version <= read2_version: PASS
    - If read1_version == 2 and read2_version == 1: MR_VIOLATION

Phase 6: Partition Healing & Cluster Recovery (finally block)
  - Remove all blackhole routes via 'ip route del blackhole'.
  - Poll until all 3 nodes report UN, Live=3, Unreachable=0, and schema agreed.

Phase 7: Post-Recovery Reconciliation Probe
  - Issue read at CL=QUORUM across healed cluster to record reconciled state.

Phase 8: Trial Logging
  - Record complete trial parameters, coordinators, read 1/2 versions,
    regression flag, classification, and failure mechanism into network_partition.csv.


6. CLASSIFICATION TAXONOMY
--------------------------
1. PASS:
   first_read_version <= second_read_version (non-decreasing sequence).

2. MR_VIOLATION:
   first_read_version == 2 and second_read_version == 1 (version regression).

3. OPERATION_FAILURE:
   Operation could not complete due to partition constraints:
   - WRITE_TIMEOUT on CL=ALL write in P8.
   - READ_TIMEOUT on CL=ALL read in P9.
   Failed operations are NEVER classified as MR violations.

4. SETUP_ERROR:
   Pre-trial baseline write (CL=ALL) failed after retries prior to injection.


7. OUTPUT ARTIFACTS
-------------------
- monotonic_reads/results/network_partition.csv (raw trial observations)
- monotonic_reads/results/network_partition_summary.csv (aggregated metrics)
